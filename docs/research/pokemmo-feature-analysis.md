## 1. Scope, provenance, and evidence standard

The owner supplied `C:\ProgramData\Microsoft\Windows\Start Menu\Programs\PokeMMO` as the installation entry point. Its two Windows shortcuts point to `C:\Program Files\PokeMMO` (game and uninstaller). On 2026-11-04 I surveyed that target's directory names, file extensions, sizes, and selected **setting key names without values**. The owner said no gameplay recordings, screenshots, or written observations are currently available. The installation contains one screenshot file, but the owner did not identify it as a reference capture, so I did not view or copy it. I did not launch or play the game.

Evidence labels used below:

- **L** — local, read-only file metadata or nonsecret setting *key names*, observed on 2026-11-04. Local files reveal available categories, not runtime behavior or an internal architecture.
- **D** — PokeMMO's public support documentation, consulted 2026-11-04. It describes published user-facing behavior; it is **not** a local gameplay observation and may differ by version/platform.
- **P** — current PokeNavis repository state or approved owner decision, with a repository link. This is the authority for our own requirements.
- **H** — hypothesis or new PokeNavis proposal. It needs owner review and, where appropriate, a later manual reference check.

**Not accessible or verified:** no owner-supplied gameplay capture or account session; no manual timing, UI layout, battle turn sequence, party/storage workflow, PvP queue, quest feedback, or live multiplayer test. I did not inspect executable/cache/packaged/mod/ROM contents, disassemble or unpack files, read private logs, saved credentials or ROM paths/values, inspect memory/network traffic, or automate input. No third-party asset or screenshot is included in this repository. The visible installation has an empty `roms/` folder, but ROM availability elsewhere was not sought or inferred. The exact client version was not established from its binary or private runtime data.

The [official penalty policy](https://support.pokemmo.com/knowledgebase/article/penalty-policy) and our [protocol](../REFERENCE-RESEARCH.md) are practical boundaries for this work. Public support documentation supplies design context; no PokeMMO code, data, creative content, names, maps, dialogue, or UI artwork should enter PokeNavis. The comparison below treats features as general interaction patterns and defines original behavior independently.

**Independent PokeNavis direction (H):** eventually define a versioned, declarative theme package containing color tokens, fonts with clear licenses, and UI spacing rules, validated before load; never execute arbitrary mod scripts as themes. Tests should reject an unsupported manifest version, missing licensed assets, path traversal, and invalid contrast tokens; smoke test keyboard/controller navigation and reset after a bad theme. This is a later platform proposal, not Phase 1 scope.

## 3. Feature analysis: published behavior → independent design

The **input → visible transition → feedback → edge case** statements are explicitly limited to cited support documentation. Where a step is not documented, it is marked unverified. PokeNavis implementation and tests below are proposals unless labeled already present (P).

### 3.1 Overworld movement, camera and input

**D:** The [run/toggle-run guide](https://support.pokemmo.com/knowledgebase/article/how-to-run-and-toggle-run) describes a story-gated run capability, hold-to-run input, a toggle option, and remappable controls. The [zoom guide](https://support.pokemmo.com/knowledgebase/article/zoom-level) describes display-size-dependent framing and video settings. **Unverified:** local movement speed, collision response, camera easing, edge behavior, and the exact UI prompt when run is unavailable. **P:** PokeNavis already has four-direction movement, collision, bounded camera and transitions ([PN-002](../PN-002-SPEC.md)); Godot 4.7.2/GDScript is pinned ([D-016](../DECISIONS.md)).

**Inferred requirement (H):** movement should be responsive and input-agnostic; the run state and zoom must have clear, accessible feedback. **Architecture:** keep a Godot `InputRouter` (bindings and device prompts) separate from a `PlayerMotor` (desired direction and speed), `CollisionMap`/`CharacterBody2D`, and `CameraRig` (bounds and zoom). For future multiplayer, let the client predict presentation while the server validates positions/zone membership; do not trust client-reported teleportation. **Improvement:** consistent camera framing across viewport sizes, user-adjustable text/UI scale independent of world zoom, explicit run availability, and an accessibility option for toggle versus hold. **Tests:** unit tests for normalized cardinal/diagonal speed and lock priority; Godot physics tests for wall sliding, narrow passages, camera bounds and return spawn; manual keyboard/controller/mobile input and small-window readability checks.

### 3.2 World transitions and region progression

**D:** [Traveling System](https://support.pokemmo.com/knowledgebase/article/traveling-system) describes an initial region-change gate based on progress, NPC travel, and a limited early return path. A player initiates travel at a travel NPC → location changes → the return option depends on progression. **Unverified:** loading time, confirmation UI, arrival handling, disconnected-session recovery. **P:** PokeNavis has a different approved rule: start in any released region; unlock travel to a *new* region only after completing the active region's main story and League/equivalent ([D-004/D-005](../DECISIONS.md)). Existing Village↔Route transitions are a small prototype, not regional travel.

**Inferred requirement (H):** show the exact gate and safe destination before travel. **Architecture:** `TravelPolicy` evaluates versioned `RegionProgress`/`CompletionChecklist`; `TransitionCoordinator` owns source/destination, a validated arrival marker, fade/loading state, and rollback if destination load fails. In the MMO, the server authorizes the policy and commits zone change atomically; the Godot scene only presents it. **Improvement:** explicit unmet requirements and a preview of what changes, with no hidden one-way trap. **Tests:** table-driven locked/unlocked and revisit cases; transition interruption/retry; safe spawn when an arrival tile is blocked; server rejection of forged progress; manual clarity checks on the gate text.

### 3.3 NPC interaction and dialogue

**D:** The travel and rematch guides describe NPC-mediated actions and, for some rematches, differing visual readiness cues ([travel](https://support.pokemmo.com/knowledgebase/article/traveling-system), [rematches](https://support.pokemmo.com/knowledgebase/article/trainer-and-gym-leader-rematches)). They do not specify generic dialogue timing or line advancement. **Unverified:** PokeMMO interaction radius, debounce, dialogue focus, cancellation, text speed, and screen-reader behavior. **P:** PokeNavis PN-003 already has a reusable NPC, proximity prompt, separate three-line data and dialogue panel, E/Enter advancement, Escape cancellation, and movement lock ([PN-003](../PN-003-SPEC.md)).

**Inferred requirement (H):** interaction feedback must remain consistent when multiple NPCs or modal windows compete for input. **Architecture:** evolve the current Godot NPC into an `Interactable` interface and an `InteractionController` that ranks nearby targets, owns focus, and emits semantic `DialogueOpened`/`DialogueClosed` events. A `DialoguePresenter` reads original versioned dialogue data and supports localization; quest or travel effects are commands authorized by their respective services, never side effects hidden in text rendering. **Improvement:** one visible target at a time, remappable prompts, optional instant text, and a transcript/repeat option. **Tests:** overlapping NPC focus, line advance per press, held-key debounce, leave-range/scene-change cancellation, missing translation fallback, and manual keyboard/controller focus order.

### 3.4 Battle turn flow and combat presentation — most relevant to PN-004

**L:** General settings key names include battle presentation categories (camera movement, size, notifications, damage display and replay), but reveal no combat rule or current value. **D:** The [rematch guide](https://support.pokemmo.com/knowledgebase/article/trainer-and-gym-leader-rematches) establishes repeatable trainer battles with eligibility conditions, and the [penalty policy](https://support.pokemmo.com/knowledgebase/article/penalty-policy) references laddered PvP. Neither source documents an exact action menu, priority order, move formulas, turn timing, switching rules, faint handling, or battle log. **Unverified:** all such local gameplay behavior. Do not derive a ruleset from filenames or assume a Pokémon-generation formula.

**Inferred requirement (H):** a battle system needs a complete, replayable record of accepted actions and resulting events, while the client shows legal choices and understandable feedback. **Architecture:** a pure, deterministic TypeScript `BattleEngine` consumes a versioned `BattleState`, `BattleAction[]`, a ruleset/content version and an injected deterministic RNG; it returns a new state plus ordered, typed `BattleEvent[]` ([architecture boundary](../ARCHITECTURE.md)). A server `BattleOrchestrator` authenticates participants, validates command sequence/idempotency and owns clocks/reconnect; a Godot adapter displays legal actions and renders events without deciding outcomes. **Improvement:** readable turn timeline, clear illegal-action reason, reduced-motion/skip-animation mode, explicit pending/confirmed actions, and replay from initial state + seed/action stream. These are original PokeNavis goals, not claims about PokeMMO internals.

**PN-004 proposal, subject to owner approval:** specify the smallest contract first: stable battle/participant/creature IDs; active slots and party references; HP and a narrowly approved status subset; turn number and phase; legal-action query; discriminated `Move`, `Switch`, `Item`/`Forfeit` action types only if in first-slice scope; event kinds such as `ActionAccepted`, `ActionRejected`, `TurnStarted`, `MoveAttempted`, `DamageApplied`, `CreatureFainted`, `SwitchCompleted`, `BattleEnded`; event ordering and version fields. Define whether rejected actions mutate state (recommended: no), how simultaneous actions resolve, how an RNG seed is recorded, and what a terminal state forbids. The exact move subset, damage/status formula, capture, items, switching costs, priority/speed/ties, PvP formats and generation policy remain **open** in [DECISIONS.md](../DECISIONS.md); this report does not settle them.

**Tests:** TypeScript schema validation and discriminated-union exhaustiveness; same initial state/actions/seed → identical state and event sequence; illegal/stale/duplicate action → explicit rejection and unchanged state; HP bounds and one terminal result; ordered faint/switch/end events; replay equivalence; fuzz/property cases for malformed actions; Godot contract tests that UI rendering cannot mutate engine state; later server tests for forged actions and reconnect replay. A manual battle reference capture, if owner-supplied later, should record each chosen action, visible pending indicator, animation/log ordering and cancellation timing, without trying to infer internal code.

### 3.5 Party, storage and capture

**D:** The [GTL guide](https://support.pokemmo.com/knowledgebase/article/the-gtl-system) says purchased creatures can go to a team if space exists, otherwise to mail, depending on access path; the [mail guide](https://support.pokemmo.com/knowledgebase/article/mail-system) discusses transferring creatures between characters. This shows capacity and destination feedback matter, but no local party/storage workflow was observed. **Unverified:** reorder controls, box search, capture overflow, comparison UI, and persistence. **P:** PokeNavis party/capture/storage are future PN-008/PN-009 work ([TASKS](../TASKS.md)).

**Inferred requirement (H):** ownership and location must never be ambiguous. **Architecture:** a versioned `CreatureInstance` with stable ID, `PartySlot` and `StorageLocation` references, and a single transfer service that atomically moves an instance between locations; Godot presents filtered lists and drag/drop/keyboard actions as commands. Offline save initially persists the same domain events; online server becomes authoritative. **Improvement:** preview the destination before capture/purchase, searchable storage, undo for local reorder, and confirmation for irreversible transfer. **Tests:** capacity boundaries, duplicate-ID exclusion, crash/retry idempotency, reorder stability, save/load round trip, and controller/keyboard accessibility.

### 3.6 Quests, story gates and repeatable activities

**D:** The [rematch guide](https://support.pokemmo.com/knowledgebase/article/trainer-and-gym-leader-rematches) documents repeat eligibility using both elapsed time and other completed battles; the [storyline support page](https://support.pokemmo.com/knowledgebase/article/questions-about-storyline) directs stuck players to walkthroughs. **Unverified:** quest journal, map markers, hidden objectives, exact state feedback. **P:** PokeNavis requires optional side/secret/weekly missions and explicit regional completion gates ([D-005 through D-007](../DECISIONS.md)); no quest system exists yet.

**Inferred requirement (H):** progress must be explainable and auditable without forcing optional content into the main path. **Architecture:** data-defined `QuestDefinition` with versioned prerequisites/objectives/rewards, per-character `QuestProgress`, an event-driven objective evaluator, and a separate `RegionCompletionPolicy`. For a later MMO, server-issued events advance progress; client UI cannot self-award completion. **Improvement:** journal entries that show known unmet prerequisites, optional discovery hints, exact reset time for weekly activities, and a completion checklist that distinguishes main story from optional 100%. **Tests:** prerequisite graphs (including cycles), duplicate event delivery, deadline boundary/time zone, region revisit, optional task exclusion from story gate, and UI comprehension checks.

### 3.7 Multiplayer presence, chat and social controls

**D:** [Changing Channels](https://support.pokemmo.com/knowledgebase/article/changing-channels) says players must be on the same channel to see each other and provides a channel selector; [chat settings](https://support.pokemmo.com/knowledgebase/article/chat-settings) support language filters and editable tabs; [friends/blocked lists](https://support.pokemmo.com/knowledgebase/article/managing-friends-and-blocked-lists) describe nearby-player and social flows. **Unverified:** movement interpolation, crowd limits, message latency, moderation UI, and reconnect behavior. **P:** PokeNavis has no multiplayer server yet; [architecture](../ARCHITECTURE.md) assigns position, presence and chat validation to future server modules.

**Inferred requirement (H):** who is visible and why should be clear, and communication should respect privacy and moderation choices. **Architecture:** server-owned `ZonePresence` subscriptions keyed by zone/instance, validated movement intents, separate chat channels with rate limits and moderation, social graph/block filtering, and minimal client presence snapshots. **Improvement:** show instance/channel identity and friend rendezvous status in plain language; independent chat font scaling, muted notifications and opt-in bubble visibility. **Tests:** two-client join/leave/reconnect, no cross-instance leakage, block/filter enforcement, chat rate limits, out-of-order movement updates, and screen-reader/keyboard navigation.

### 3.8 PvP, ranked formats and replays

**D:** The [penalty policy](https://support.pokemmo.com/knowledgebase/article/penalty-policy) mentions laddered PvP, official rankings and match manipulation. **L:** a general setting key name references instant replay; this proves only a setting category, not that replay worked in this installation. **Unverified:** queue screens, team validation, rating formula, timer, spectator/replay flow, disconnect judgment. **P:** PokeNavis PvP is a later milestone; separate versioned ranked rulesets are proposed in [GDD](../GDD.md), and the server must own official outcomes ([architecture](../ARCHITECTURE.md)).

**Inferred requirement (H):** a match must state its format, eligible team, timer and result evidence before it affects ranking. **Architecture:** `FormatRegistry` stores immutable ruleset versions; `TeamValidator` checks eligibility; `Matchmaker` creates a match; the battle orchestrator records a replay/action log; `RatingService` consumes only verified terminal results once. **Improvement:** pre-queue eligibility preview, precise rejection reasons, accessible battle log/replay, and public format/version history. **Tests:** format migration, ineligible team denial, disconnect/timeout policy once approved, duplicate result delivery, replay integrity, rating conservation/invariants for the chosen formula, and match-manipulation monitoring scenarios.

### 3.9 Economy, direct trade, market and mail

**D:** The [GTL guide](https://support.pokemmo.com/knowledgebase/article/the-gtl-system) describes searchable listings, a listing fee shown before confirmation, a progression gate for buying/listing, and different delivery locations; [mail](https://support.pokemmo.com/knowledgebase/article/mail-system) supports transferring assets but cautions against non-atomic mail trades; [trade-loss advice](https://support.pokemmo.com/knowledgebase/article/assets-lost) stresses recipient/content review. **Unverified:** local listing UI, final confirmation text, concurrent purchase handling, dispute flow. **P:** PokeNavis economy/trade is future work and competitive transactions must be server-authoritative ([architecture](../ARCHITECTURE.md)).

**Inferred requirement (H):** every ownership/currency transfer must be atomic, idempotent, and explainable to the player. **Architecture:** `InventoryLedger` records immutable debits/credits, `TradeSession` requires both parties to approve a versioned offer snapshot, `MarketListing` reserves assets and price, and `MailDelivery` transfers a completed entitlement rather than acting as an unsafe escrow substitute. PostgreSQL transactions and unique idempotency keys guard settlement. **Improvement:** side-by-side final offer review, delivery destination preview, explicit fees, receipt/history and reversible cancellation *before* settlement. **Tests:** simultaneous purchase race, double-click settlement, disconnect between approvals, changed-offer invalidation, full party/storage delivery, non-tradable protection exclusion, and audit reconciliation. Exact market fees/economic rules remain unapproved.

### 3.10 Accessibility, settings and customization

**D:** Public guides document mod/theme import, remappable controls, chat filters, zoom and controller support; the [controller guide](https://support.pokemmo.com/knowledgebase/article/setting-up-a-controller) explicitly notes some UI/platform gaps. **L:** local general settings key names show UI scaling, text speed, audio controls, mobile controls and theme categories. **Unverified:** actual installed theme behavior, contrast, localization quality, settings persistence and controller coverage. **P:** PokeNavis targets Windows first and Android later ([ROADMAP](../ROADMAP.md)); only a small Godot prototype exists.

**Inferred requirement (H):** every core flow should work with keyboard and, when supported, controller/mobile without relying on visual color alone. **Architecture:** one semantic `InputAction` map, focus-navigation rules shared by Godot scenes, versioned preferences with migrations, presentation tokens for themes, separate localization strings, and a fallback theme. **Improvement:** UI scale and world zoom independently adjustable, contrast and reduced-motion options, per-channel chat controls, and a visible binding-conflict checker. **Tests:** settings round trip/migration, invalid theme rollback, all-dialog focus traversal, binding conflict checks, localization overflow, resolution matrix and accessibility review with real devices before release.

| Customization | Themes, controls and chat preferences | Basic remappable input and scale | Declarative validated themes, safe fallback and complete focus support | Medium / medium / UI architecture |

## 5. Incremental plan and PN-004 handoff

1. **Now — research review (REF-001):** owner checks factual boundaries and priorities. If desired, provide brief manual captures/notes for the unverified flows listed above; add a separate evidence appendix later. This PR changes documentation only.
2. **Before PN-004 Ready:** owner approves a minimal original battle-rules scope and resolves the decisions needed for the first schema (action set, turn phases, RNG record, a small move/status subset, switch/faint/end semantics, and offline TypeScript↔Godot adapter boundary). Record explicit decisions in [DECISIONS.md](../DECISIONS.md) and write PN-004 acceptance tests. This report does **not** change PN-004's Backlog status.
3. **PN-004 implementation (separate authorized task):** create typed state/action/event contracts and validation, with deterministic/replay test vectors using original content. No PokeMMO assets or rules dump.
4. **PN-005/006/007/008/009:** implement pure simulation, Godot presentation, encounters, capture/party/storage and versioned local save in dependency order. Keep visual choices outside the engine.
5. **Later multiplayer/PvP/economy:** add server-authoritative commands, transactional ledgers and versioned formats after the offline slice is proven; load, concurrency and reconciliation tests become release gates.

## 7. Reproducibility and review checklist

- Local survey: PowerShell `Get-ChildItem`/`Get-Item` on only the owner-supplied Start Menu folder and its resolved installation target; `WScript.Shell.CreateShortcut` resolved the `.lnk` targets. `Get-Content` was used on the general `.properties` file **only to extract property names before output**, never values; saved credentials, the numbered config file, logs and other file contents were not read. Commands were read-only.
- Public reference: the specific official support links in each feature section, consulted 2026-11-04. They are cited near the claims they support; no uncited gameplay behavior is treated as observed.
- PokeNavis baseline: [STATUS](../STATUS.md), [TASKS](../TASKS.md), [DECISIONS](../DECISIONS.md), [ARCHITECTURE](../ARCHITECTURE.md), [GDD](../GDD.md), and [ROADMAP](../ROADMAP.md) from current `main` when this branch was created.
- Review questions: Are the evidence labels accurate? Are PN-004 proposals clearly unapproved? Are any local names/values, personal data, protected images, third-party code or ROM contents present? Are the proposed tests independent of PokeMMO's internal implementation?
